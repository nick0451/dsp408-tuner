> ### On #14 — refuted in mechanism, right in spirit
>
> The claim was that decoding and re-encoding blocks 31 and 35 would drop bytes
> we do not understand. It does not: both consume all eight payload bytes into
> named fields and re-emit them at identical positions.
>
> But investigating it found something worse. **Block 34's decode is
> semantically wrong.** `protocol.OutputBlock` calls DataID 34 `MIX_IN_9_16`;
> the device's own bulk readback returns dynamics-shaped bytes there on every
> channel, and `ddp.py` has always called it "dynamics A". The two modules have
> disagreed since both were written and nobody noticed.
>
> So the underlying worry — that read-modify-write through blocks you do not
> understand is dangerous — was correct, by a different mechanism than claimed.
> **Blocks 34 and 35 are excluded from every write path** (`UNVERIFIED_OUTPUT_BLOCKS`).
> "Refuted" on row 14 must never be read as "34/35 are safe to write."

### What the review missed

A review is a prompt to audit, not a complete audit. Checking its claims turned
up two real gaps it did not raise:

- **`group_delay_samples` was unguarded.** The timing-reference rule names
  delay, phase *and group delay*. Delay and phase had guarded accessors on
  `Measurement`; group delay existed only as a free function in `metrics.py`
  taking a bare impulse array, which has no measurement to check. Fixed:
  `Measurement.group_delay_samples` now raises, and the free function carries a
  warning.
- **`IncomparableProvenance` had zero test coverage.** The `verify.py`
  indeterminate path was well tested; the *raise* branch that guards ad-hoc
  comparisons outside the optimizer was never exercised. Fixed with a case per
  branch of `comparable_to`.

## Round 2 — the counter-pass on the plan

No design errors. **Three sequencing errors**, one of them destructive.

| # | Finding | Verdict |
|---|---|---|
| 1 | The proposed operator capture would destroy the working tune | **Confirmed — the serious one.** Step 2 recalled a preset while the working area held the only copy of the live state. Preset recall overwrites the working area and there is no undo, so the tune would have been lost *before* anything archived it, and the subsequent store would have archived the wrong tune. Reordered to store → recall other → recall back → verify. |
| 2 | The RBJ measurement was scheduled behind a dependency it does not have | **Confirmed.** It needs only the vendor app, the existing rig and `biquad.py`. Pulled ahead of all M3 work, since M3's oracles would otherwise be built on unverified unit conversions. |

Plus hygiene, all accepted: named defences given modules and tests; the
crash-mid-write reconcile made an explicit oracle; the session oracle required
to document its frozen fields; the 296-byte bulk reply (16 link chunks) made an
explicit reader-oracle case; the narrow-channel linearity fix listed as
out-of-scope so it stays tracked rather than vanishing from both lists.

## What round 3 changed in the code

Four things, all from confirmed findings:

- **`LinkIdMismatch`** — the top first-contact risk now diagnoses itself on the
  first offending reply instead of after eight discards, and carries the value
  the device used so the retry is informed. `--link-id` exposes it on the probe.
- **`snapshot.compare_system()`** — global state is now comparable, not merely
  captured. The master volume is `DataType 9` channel 5 and one write moves
  every output.
- **`safety.ceiling_for_device_state()`** — rule 6 as code. The worked example
  from `CLAUDE.md` is a test: a +6 dB channel with a +12 dB band yields a
  −38 dBFS ceiling, and a −18 dBFS stimulus is refused.
- **`DeviceImage.system`** — the fake modelled the master volume as a module
  constant, which made the drift in finding #9 untestable. Per-instance now.

## What the reviewer got right that is worth generalising

Finding #1 is the most useful thing in this round, and not because of the
paragraph. **A document becomes dangerous at exactly the point it becomes
trustworthy.** STATE.md is now authoritative enough that a stale line in it
propagates instead of being questioned — and the staleness was created by the
same velocity that made it good. The countermeasure is not to write less but to
re-read the sections a session *touched* before ending it, which is what this
round forced and what the two contradictions would otherwise have cost.

Finding #8/#9 is the second: **"captured" and "compared" are different
properties, and the gap between them is invisible.** The data was there all
along. Nothing was missing; nothing looked wrong; and the check that would have
used it did not exist.

### Amendment to 7a, same evening

The reviewer was right that the ambiguity existed and had to be resolved. I
resolved it **by inference** — eight operator readings against eight known
`gain_raw` values, giving a clean and confident answer: *the app displays
`raw/10`, so the display never confirmed the offset.* I wrote that into
`CLAUDE.md` as a correction, alongside a note that it deserved one question to
the operator.

The operator then answered the question: **there are two vendor apps.** The
iOS app shows output gain 0–60 and input gain 0–100; the Android app — the one
on the debugging phone, the one in every HCI capture — shows `−10.0 dB`. Both
readings were literal. The original claim was right, and my correction of it
was wrong.

Two things worth keeping:

- **Hedging one sentence while asserting in the surrounding paragraphs is not
  hedging.** The note saying "worth one question to confirm" sat directly under
  a heading stating the wrong conclusion as fact. A reader after a context
  reset takes the heading. **If a claim is worth flagging as unconfirmed, it is
  not yet worth writing as a correction** — leave the original standing and
  record the open question beside it.
- **This is the fifth time the ask-the-operator rule has paid**, and the second
  today. The rule already says an operator observation that contradicts the
  repository wins; it now also has a case where the operator contradicted a
  *correction* and restored the original.

It also produced something new: **the iOS app reaches input gain.** `DataType 3`
is unmapped precisely because it never appeared in the Android captures, and
this is the first evidence that a vendor path to those parameters exists.

## The pattern, twice running

Round 3 named "a document becomes dangerous at the point it becomes
trustworthy" and prescribed re-reading the sections a session touched before
ending it. Round 4 found the same species again, and the sweep that *did* run
caught the mechanical defects (placeholders, "never transmitted") while missing
every semantic one: the unknowns table not collecting evidence the session
produced, an overclaim about the snapshot's coverage, an evidence-grade
attribution pointing at the wrong evidence.

**So the countermeasure needs sharpening, not repeating.** A grep-shaped sweep
finds grep-shaped errors. The specific gap is that **the open-questions table is
never read as part of writing up a session** — items 2 and 7a are both failures
to *collect* on evidence, not failures to describe it.

Concretely, added to the end-of-session routine: **for every unknown whose
"when it bites" column names something that just happened, write down what the
session showed — including "still open, and here is why the evidence we got does
not settle it."** Item 2's padding row is the model: reads were padded and
answered, so padding is tolerated; the one unpadded frame is confounded by the
USB window and proves nothing; the question survives with its evidence attached.
